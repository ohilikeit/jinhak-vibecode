# Skill 작성자를 위한 모범 사례

> 작업에 맞게 범위가 잘 설정되고 적절히 보정된 skill을 작성하는 방법.

## 실제 전문성에서 시작하기

skill 작성에서 흔히 빠지는 함정은 도메인별 컨텍스트를 제공하지 않은 채 LLM에게 skill을 생성하라고 요청하는 것입니다 — 오로지 LLM의 일반적인 학습 지식에만 의존하는 것이죠. 그 결과는 skill을 가치 있게 만드는 구체적인 API 패턴, 엣지 케이스, 프로젝트 관례 대신 모호하고 일반적인 절차("오류를 적절히 처리하세요", "인증 모범 사례를 따르세요")로 끝납니다.

효과적인 skill은 실제 전문성에 기반합니다. 핵심은 도메인별 컨텍스트를 작성 과정에 투입하는 것입니다.

### 실습 작업에서 추출하기

에이전트와의 대화 중에 실제 작업을 완수하면서, 그 과정에서 컨텍스트, 수정 사항, 선호도를 제공하세요. 그런 다음 재사용 가능한 패턴을 추출하여 skill로 만드세요. 다음에 주목하세요:

* **효과가 있었던 단계** — 성공으로 이어진 행동의 순서
* **당신이 한 수정** — 에이전트의 접근 방식을 조정한 지점들 (예: "Y 대신 라이브러리 X를 사용하세요", "엣지 케이스 Z를 확인하세요")
* **입력/출력 형식** — 들어오고 나가는 데이터가 어떤 모습이었는지
* **당신이 제공한 컨텍스트** — 에이전트가 이미 알고 있지 않았던 프로젝트별 사실, 관례 또는 제약 조건

### 기존 프로젝트 산출물에서 종합하기

기존 지식의 본체가 있다면, 그것을 LLM에 투입하고 skill을 종합해 달라고 요청할 수 있습니다. 일반적인 "데이터 엔지니어링 모범 사례" 글에서 종합한 것보다, 팀의 실제 사고 보고서와 runbook에서 종합한 데이터 파이프라인 skill이 더 나은 성능을 보일 것입니다. 왜냐하면 그것은 *당신의* 스키마, 실패 모드, 복구 절차를 포착하기 때문입니다. 핵심은 일반적인 참고 자료가 아니라 프로젝트별 자료입니다.

좋은 출처 자료에는 다음이 포함됩니다:

* 내부 문서, runbook, 스타일 가이드
* API 사양, 스키마, 설정 파일
* 코드 리뷰 코멘트와 이슈 트래커 (반복되는 우려 사항과 리뷰어의 기대치를 포착)
* 버전 관리 이력, 특히 패치와 수정 사항 (실제로 무엇이 변경되었는지를 통해 패턴을 드러냄)
* 실제 실패 사례와 그 해결책

## 실제 실행으로 다듬기

skill의 초안은 보통 다듬기가 필요합니다. 실제 작업에 대해 skill을 실행한 다음, 그 결과를 — 실패만이 아니라 전부를 — 작성 과정에 다시 투입하세요. 다음을 질문하세요: 무엇이 거짓 양성을 유발했나? 무엇을 놓쳤나? 무엇을 잘라낼 수 있나?

실행 후 수정의 단 한 번의 패스만으로도 품질이 눈에 띄게 향상되며, 복잡한 도메인은 종종 여러 번의 패스로부터 이득을 봅니다.

<Tip>
  최종 출력만이 아니라 에이전트의 실행 트레이스를 읽으세요. 에이전트가 비생산적인 단계에 시간을 낭비한다면, 흔한 원인은 너무 모호한 지시(에이전트가 작동하는 것을 찾기 전에 여러 접근법을 시도함), 현재 작업에 적용되지 않는 지시(에이전트가 그래도 따름), 또는 명확한 기본값 없이 너무 많은 옵션이 제시된 경우입니다.
</Tip>

테스트 케이스, 단언문(assertion), 채점 등 더 구조화된 반복 접근에 대해서는 [Skill 출력 품질 평가하기](/skill-creation/evaluating-skills)를 참조하세요.

## 컨텍스트를 현명하게 쓰기

skill이 활성화되면, 그 전체 `SKILL.md` 본문이 대화 이력, 시스템 컨텍스트, 그리고 다른 활성 skill과 함께 에이전트의 컨텍스트 윈도우에 로드됩니다. skill의 모든 토큰은 그 윈도우 안의 다른 모든 것과 에이전트의 주의를 두고 경쟁합니다.

### 에이전트가 부족한 것을 추가하고, 알고 있는 것은 생략하라

skill 없이는 에이전트가 *알지 못할* 것에 집중하세요: 프로젝트별 관례, 도메인별 절차, 자명하지 않은 엣지 케이스, 그리고 사용할 특정 도구나 API. PDF가 무엇인지, HTTP가 어떻게 작동하는지, 데이터베이스 마이그레이션이 무엇을 하는지 설명할 필요는 없습니다.

````markdown theme={null}
<!-- 너무 장황함 — 에이전트는 이미 PDF가 무엇인지 알고 있음 -->
## PDF 텍스트 추출

PDF(Portable Document Format) 파일은 텍스트, 이미지 및 기타 내용을
포함하는 일반적인 파일 형식입니다. PDF에서 텍스트를 추출하려면
라이브러리를 사용해야 합니다. pdfplumber는 대부분의 경우를 잘 처리하므로
권장됩니다.

<!-- 더 나음 — 에이전트가 스스로 알지 못할 부분으로 바로 직진 -->
## PDF 텍스트 추출

텍스트 추출에는 pdfplumber를 사용하세요. 스캔된 문서의 경우
pdf2image와 pytesseract로 대체 사용하세요.

```python
import pdfplumber

with pdfplumber.open("file.pdf") as pdf:
    text = pdf.pages[0].extract_text()
```
````

각 콘텐츠 조각에 대해 자문해 보세요: "이 지시 없이 에이전트가 이것을 틀리게 할까?" 답이 아니오라면, 잘라내세요. 확실하지 않다면, 테스트하세요. 그리고 에이전트가 skill 없이도 전체 작업을 잘 처리한다면, 그 skill은 가치를 더하지 못하고 있을 수 있습니다. 이를 체계적으로 테스트하는 방법은 [Skill 출력 품질 평가하기](/skill-creation/evaluating-skills)를 참조하세요.

### 일관된 단위를 설계하라

skill이 무엇을 다룰지 결정하는 것은 함수가 무엇을 해야 할지 결정하는 것과 같습니다: 다른 skill과 잘 결합되는, 일관된 작업 단위를 캡슐화하기를 원합니다. 너무 좁게 범위가 설정된 skill은 단일 작업에 여러 skill을 로드하게 만들어, 오버헤드와 충돌하는 지시의 위험이 있습니다. 너무 넓게 범위가 설정된 skill은 정확히 활성화되기가 어렵습니다. 데이터베이스를 쿼리하고 결과를 포맷하는 skill은 하나의 일관된 단위일 수 있지만, 데이터베이스 관리까지 다루는 skill은 아마도 너무 많은 일을 하려는 것입니다.

### 적당한 수준의 세부 사항을 목표로 하라

지나치게 포괄적인 skill은 도움보다 해가 될 수 있습니다 — 에이전트가 관련 있는 것을 추출하려 애쓰게 되고, 현재 작업에 적용되지 않는 지시에 의해 촉발된 비생산적인 경로를 추구할 수 있습니다. 작동하는 예제와 함께 간결하고 단계적인 안내가 보통 망라적인 문서보다 더 나은 성능을 보입니다. 모든 엣지 케이스를 다루고 있는 자신을 발견한다면, 대부분이 에이전트 자체의 판단으로 더 잘 처리되는지 고려해 보세요.

### 점진적 공개로 큰 skill을 구조화하라

[사양](/specification#progressive-disclosure)은 `SKILL.md`를 500줄, 5,000 토큰 미만으로 유지할 것을 권장합니다 — 매 실행마다 에이전트가 필요로 하는 핵심 지시만요. skill에 정당하게 더 많은 콘텐츠가 필요한 경우, 자세한 참고 자료는 `references/` 또는 유사한 디렉터리의 별도 파일로 이동하세요.

핵심은 에이전트에게 각 파일을 *언제* 로드할지 알려주는 것입니다. "API가 200이 아닌 상태 코드를 반환하면 `references/api-errors.md`를 읽으세요"는 일반적인 "자세한 내용은 references/를 참조하세요"보다 더 유용합니다. 이렇게 하면 에이전트가 미리가 아닌 필요에 따라 컨텍스트를 로드할 수 있는데, 이것이 [점진적 공개](/specification#progressive-disclosure)가 작동하도록 설계된 방식입니다.

## 제어 보정하기

skill의 모든 부분이 같은 수준의 지시성(prescriptiveness)을 필요로 하는 것은 아닙니다. 지시의 구체성을 작업의 취약성에 맞추세요.

### 구체성을 취약성에 맞춰라

여러 접근법이 유효하고 작업이 다양성을 허용할 때 **에이전트에게 자유를 주세요**. 유연한 지시의 경우, *왜* 그런지 설명하는 것이 엄격한 지시보다 더 효과적일 수 있습니다 — 지시 뒤의 목적을 이해하는 에이전트는 컨텍스트에 따라 더 나은 결정을 내립니다. 코드 리뷰 skill은 정확한 단계를 처방하지 않고도 무엇을 찾을지 설명할 수 있습니다:

```markdown theme={null}
## 코드 리뷰 프로세스

1. 모든 데이터베이스 쿼리에 대해 SQL 인젝션을 점검하세요 (매개변수화된 쿼리 사용)
2. 모든 엔드포인트에서 인증 점검을 검증하세요
3. 동시성 코드 경로에서 경쟁 조건을 찾으세요
4. 오류 메시지가 내부 세부 사항을 누설하지 않는지 확인하세요
```

작업이 취약하거나, 일관성이 중요하거나, 특정 시퀀스를 따라야 할 때는 **지시적으로 작성하세요**:

````markdown theme={null}
## 데이터베이스 마이그레이션

정확히 이 시퀀스를 실행하세요:

```bash
python scripts/migrate.py --verify --backup
```

명령을 수정하거나 추가 플래그를 더하지 마세요.
````

대부분의 skill은 혼합되어 있습니다. 각 부분을 독립적으로 보정하세요.

### 메뉴가 아니라 기본값을 제공하라

여러 도구나 접근법이 작동할 수 있을 때, 기본값을 하나 선택하고 대안은 동등한 옵션으로 제시하기보다는 간단히 언급하세요.

````markdown theme={null}
<!-- 너무 많은 옵션 -->
pypdf, pdfplumber, PyMuPDF, 또는 pdf2image를 사용할 수 있습니다...

<!-- 명확한 기본값과 탈출구 -->
텍스트 추출에는 pdfplumber를 사용하세요:

```python
import pdfplumber
```

OCR이 필요한 스캔된 PDF의 경우, 대신 pdf2image와 pytesseract를 사용하세요.
````

### 선언보다 절차를 선호하라

skill은 에이전트에게 특정 사례에 대해 *무엇을 생산할지*가 아니라, 어떤 부류의 문제에 *어떻게 접근할지*를 가르쳐야 합니다. 비교해 보세요:

```markdown theme={null}
<!-- 구체적인 답 — 이 정확한 작업에만 유용 -->
`orders` 테이블을 `customer_id`로 `customers`에 조인하고,
`region = 'EMEA'`로 필터링한 후, `amount` 컬럼을 합산하세요.

<!-- 재사용 가능한 방법 — 모든 분석 쿼리에 작동 -->
1. `references/schema.yaml`에서 스키마를 읽어 관련 테이블을 찾으세요
2. `_id` 외래 키 관례를 사용하여 테이블을 조인하세요
3. 사용자 요청의 필터를 WHERE 절로 적용하세요
4. 필요에 따라 숫자 컬럼을 집계하고 마크다운 표로 포맷하세요
```

이것은 skill이 구체적인 세부 사항을 포함할 수 없다는 의미가 아닙니다 — 출력 형식 템플릿([출력 형식 템플릿](#templates-for-output-format) 참조), "PII를 절대 출력하지 마라" 같은 제약, 도구별 지시는 모두 가치 있습니다. 요점은 개별 세부 사항이 구체적일 때도 *접근법*은 일반화되어야 한다는 것입니다.

## 효과적인 지시를 위한 패턴

이것들은 skill 콘텐츠를 구조화하기 위한 재사용 가능한 기법입니다. 모든 skill이 이것들 전부를 필요로 하는 것은 아닙니다 — 작업에 맞는 것을 사용하세요.

### Gotchas(주의 사항) 섹션

많은 skill에서 가장 가치 있는 콘텐츠는 gotcha 목록입니다 — 합리적인 가정에 반하는 환경별 사실들입니다. 이것들은 일반적인 조언("오류를 적절히 처리하세요")이 아니라, 알려주지 않으면 에이전트가 저지를 실수에 대한 구체적인 시정입니다:

```markdown theme={null}
## Gotchas

- `users` 테이블은 소프트 삭제를 사용합니다. 쿼리에 반드시
  `WHERE deleted_at IS NULL`을 포함해야 하며, 그렇지 않으면 비활성화된 계정이 결과에 포함됩니다.
- 사용자 ID는 데이터베이스에서 `user_id`, 인증 서비스에서 `uid`,
  과금 API에서 `accountId`입니다. 세 가지 모두 같은 값을 지칭합니다.
- `/health` 엔드포인트는 데이터베이스 연결이 끊겨도 웹 서버가 실행 중이기만 하면
  200을 반환합니다. 전체 서비스 상태를 확인하려면 `/ready`를 사용하세요.
```

gotcha는 에이전트가 상황을 만나기 전에 읽도록 `SKILL.md`에 보관하세요. 에이전트에게 언제 로드할지 알려준다면 별도의 참조 파일도 작동하지만, 자명하지 않은 이슈의 경우 에이전트가 트리거를 인식하지 못할 수 있습니다.

<Tip>
  에이전트가 당신이 시정해야 할 실수를 할 때, 그 시정을 gotchas 섹션에 추가하세요. 이것은 skill을 반복적으로 개선하는 가장 직접적인 방법 중 하나입니다([실제 실행으로 다듬기](#refine-with-real-execution) 참조).
</Tip>

### 출력 형식 템플릿

에이전트가 특정 형식으로 출력을 생산해야 할 때, 템플릿을 제공하세요. 에이전트는 구체적인 구조에 대해 패턴 매칭을 잘하므로, 이는 형식을 산문으로 설명하는 것보다 더 신뢰할 만합니다. 짧은 템플릿은 `SKILL.md`에 인라인으로 둘 수 있습니다; 더 긴 템플릿이나 특정 경우에만 필요한 템플릿은 `assets/`에 저장하고 `SKILL.md`에서 참조하여 필요할 때만 로드되도록 하세요.

````markdown theme={null}
## 보고서 구조

특정 분석에 필요에 따라 섹션을 조정하면서 이 템플릿을 사용하세요:

```markdown
# [분석 제목]

## 요약
[주요 발견에 대한 한 단락 개요]

## 주요 발견
- 보조 데이터가 있는 발견 1
- 보조 데이터가 있는 발견 2

## 권장 사항
1. 구체적이고 실행 가능한 권장 사항
2. 구체적이고 실행 가능한 권장 사항
```
````

### 다단계 워크플로를 위한 체크리스트

명시적인 체크리스트는 특히 단계에 의존성이나 검증 게이트가 있는 경우, 에이전트가 진행 상황을 추적하고 단계를 건너뛰지 않도록 돕습니다.

```markdown theme={null}
## 양식 처리 워크플로

진행 상황:
- [ ] 1단계: 양식 분석 (`scripts/analyze_form.py` 실행)
- [ ] 2단계: 필드 매핑 생성 (`fields.json` 편집)
- [ ] 3단계: 매핑 검증 (`scripts/validate_fields.py` 실행)
- [ ] 4단계: 양식 채우기 (`scripts/fill_form.py` 실행)
- [ ] 5단계: 출력 검증 (`scripts/verify_output.py` 실행)
```

### 검증 루프

에이전트에게 다음으로 넘어가기 전에 자체 작업을 검증하도록 지시하세요. 패턴은 다음과 같습니다: 작업을 수행하고, 검증기(스크립트, 참조 체크리스트, 자체 검사)를 실행하고, 문제를 수정하고, 검증을 통과할 때까지 반복합니다.

```markdown theme={null}
## 편집 워크플로

1. 편집을 수행하세요
2. 검증 실행: `python scripts/validate.py output/`
3. 검증이 실패하면:
   - 오류 메시지를 검토하세요
   - 문제를 수정하세요
   - 검증을 다시 실행하세요
4. 검증이 통과될 때만 진행하세요
```

참조 문서도 "검증기" 역할을 할 수 있습니다 — 에이전트에게 마무리 전에 참조에 대해 작업을 점검하도록 지시하세요.

### 계획-검증-실행

배치 또는 파괴적 작업의 경우, 에이전트가 구조화된 형식으로 중간 계획을 만들고, 그것을 진실의 원천에 대해 검증한 다음에야 실행하도록 하세요.

```markdown theme={null}
## PDF 양식 채우기

1. 양식 필드 추출: `python scripts/analyze_form.py input.pdf` → `form_fields.json`
   (모든 필드 이름, 유형, 필수 여부를 나열함)
2. 각 필드 이름을 의도된 값에 매핑하는 `field_values.json`을 만드세요
3. 검증: `python scripts/validate_fields.py form_fields.json field_values.json`
   (모든 필드 이름이 양식에 존재하는지, 유형이 호환되는지,
   필수 필드가 누락되지 않았는지 확인)
4. 검증이 실패하면 `field_values.json`을 수정하고 다시 검증하세요
5. 양식 채우기: `python scripts/fill_form.py input.pdf field_values.json output.pdf`
```

핵심 요소는 3단계입니다: 계획(`field_values.json`)을 진실의 원천(`form_fields.json`)에 대해 점검하는 검증 스크립트. "필드 'signature\_date'를 찾을 수 없음 — 사용 가능한 필드: customer\_name, order\_total, signature\_date\_signed" 같은 오류는 에이전트에게 자체 시정에 충분한 정보를 줍니다.

### 재사용 가능한 스크립트 번들링

[skill을 반복 개선](/skill-creation/evaluating-skills)할 때, 테스트 케이스 간 에이전트의 실행 트레이스를 비교하세요. 에이전트가 매 실행마다 동일한 로직을 독립적으로 재발명하는 것을 발견한다면 — 차트 작성, 특정 형식 파싱, 출력 검증 — 그것은 한 번 테스트된 스크립트를 작성하여 `scripts/`에 번들링할 신호입니다.

스크립트 설계와 번들링에 대한 자세한 내용은 [skill에서 스크립트 사용하기](/skill-creation/using-scripts)를 참조하세요.
