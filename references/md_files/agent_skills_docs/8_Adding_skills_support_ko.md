# 에이전트에 스킬(skills) 지원을 추가하는 방법

> AI 에이전트나 개발 도구에 Agent Skills 지원을 추가하기 위한 가이드입니다.

이 가이드는 AI 에이전트 또는 개발 도구에 Agent Skills 지원을 추가하는 전체 과정을 안내합니다. 스킬 발견(discovery), 모델에게 스킬 알리기, 스킬 콘텐츠를 컨텍스트에 로드하기, 그리고 시간이 지나도 그 콘텐츠를 효과적으로 유지하기까지 전체 라이프사이클을 다룹니다.

핵심 통합 방식은 에이전트의 아키텍처와 무관하게 동일합니다. 구현 세부 사항은 다음 두 가지 요인에 따라 달라집니다.

* **스킬은 어디에 존재하는가?** 로컬에서 실행되는 에이전트는 사용자 파일시스템에서 스킬 디렉터리를 스캔할 수 있습니다. 클라우드 호스팅 또는 샌드박스 환경의 에이전트라면 API, 원격 레지스트리, 번들된 자산 등 대안적인 발견 메커니즘이 필요합니다.
* **모델은 스킬 콘텐츠에 어떻게 접근하는가?** 모델이 파일 읽기 능력을 가지고 있다면 `SKILL.md` 파일을 직접 읽을 수 있습니다. 그렇지 않다면 전용 도구를 제공하거나 프로그램적으로 스킬 콘텐츠를 프롬프트에 주입해야 합니다.

본 가이드는 이러한 차이가 중요해지는 지점을 명시합니다. 모든 시나리오를 지원할 필요는 없으며, 자신의 에이전트에 맞는 경로만 따라가면 됩니다.

**사전 요구 사항**: [Agent Skills 명세](/specification)에 대한 이해. 이 명세는 `SKILL.md` 파일 형식, 프런트매터(frontmatter) 필드, 디렉터리 컨벤션을 정의합니다.

## 핵심 원칙: 점진적 공개(progressive disclosure)

스킬을 지원하는 모든 에이전트는 동일한 3계층 로딩 전략을 따릅니다.

| 계층            | 로드되는 것                  | 시점                                | 토큰 비용                    |
| --------------- | --------------------------- | ----------------------------------- | --------------------------- |
| 1. 카탈로그     | 이름 + 설명                 | 세션 시작                           | 스킬당 약 50~100 토큰       |
| 2. 지침         | 전체 `SKILL.md` 본문        | 해당 스킬이 활성화될 때             | \<5000 토큰 (권장)          |
| 3. 리소스       | 스크립트, 참조 자료, 자산   | 지침이 해당 파일을 참조할 때        | 가변                        |

모델은 시작 시점부터 카탈로그를 보기 때문에 어떤 스킬을 사용할 수 있는지 알게 됩니다. 어떤 스킬이 관련 있다고 판단하면 전체 지침을 로드합니다. 지침이 보조 파일을 참조한다면, 모델은 필요에 따라 그 파일을 개별적으로 로드합니다.

이를 통해 기본 컨텍스트는 작게 유지하면서도 모델이 필요할 때 전문 지식에 접근할 수 있게 합니다. 20개의 스킬이 설치된 에이전트라도 20개 전체 지침의 토큰 비용을 미리 부담하지 않으며, 실제로 사용된 스킬에 대해서만 비용이 발생합니다.

## 1단계: 스킬 발견하기

세션 시작 시점에 사용 가능한 모든 스킬을 찾아 메타데이터를 로드합니다.

### 어디를 스캔할 것인가

스캔할 디렉터리는 에이전트의 환경에 따라 다릅니다. 대부분의 로컬 실행 에이전트는 최소 두 가지 범위를 스캔합니다.

* **프로젝트 수준**(작업 디렉터리 기준): 특정 프로젝트나 저장소에 종속된 스킬.
* **사용자 수준**(홈 디렉터리 기준): 해당 사용자의 모든 프로젝트에서 사용할 수 있는 스킬.

다른 범위도 가능합니다. 예를 들어 관리자가 배포한 조직 전체 스킬이나, 에이전트 자체에 번들된 스킬 등이 있습니다. 적절한 범위 집합은 에이전트의 배포 모델에 따라 결정됩니다.

각 범위 내에서 **클라이언트 전용 디렉터리**와 **`.agents/skills/` 컨벤션** 모두를 스캔하는 것을 고려하세요.

| 범위    | 경로                               | 목적                          |
| ------- | ---------------------------------- | ----------------------------- |
| 프로젝트 | `<project>/.<your-client>/skills/` | 클라이언트의 기본 위치        |
| 프로젝트 | `<project>/.agents/skills/`        | 클라이언트 간 상호 운용성     |
| 사용자  | `~/.<your-client>/skills/`         | 클라이언트의 기본 위치        |
| 사용자  | `~/.agents/skills/`                | 클라이언트 간 상호 운용성     |

`.agents/skills/` 경로는 클라이언트 간 스킬 공유를 위한 사실상의 컨벤션으로 자리 잡고 있습니다. Agent Skills 명세는 스킬 디렉터리가 어디에 있어야 하는지(내부에 무엇이 들어가는지만 정의) 규정하지 않지만, `.agents/skills/`를 스캔하면 다른 호환 클라이언트가 설치한 스킬이 자동으로 보이고, 그 반대도 가능해집니다.

<Note>
  일부 구현체는 실용적 호환성을 위해 `.claude/skills/`(프로젝트 수준과 사용자 수준 모두)도 스캔합니다. 이미 많은 기존 스킬이 그곳에 설치되어 있기 때문입니다. 그 외의 추가 위치로는 git 루트까지의 상위 디렉터리(모노레포에서 유용), [XDG](https://specifications.freedesktop.org/basedir-spec/latest/) 구성 디렉터리, 사용자가 직접 지정한 경로 등이 있습니다.
</Note>

### 무엇을 스캔할 것인가

각 스킬 디렉터리 내부에서 정확히 `SKILL.md`라는 이름의 파일을 포함한 **서브디렉터리**를 찾습니다.

```
~/.agents/skills/
├── pdf-processing/
│   ├── SKILL.md          ← 발견됨
│   └── scripts/
│       └── extract.py
├── data-analysis/
│   └── SKILL.md          ← 발견됨
└── README.md             ← 무시됨 (스킬 디렉터리가 아님)
```

실용적인 스캐닝 규칙:

* `.git/`, `node_modules/`처럼 스킬이 들어 있지 않을 디렉터리는 건너뜁니다.
* 빌드 산출물 스캔을 피하기 위해 선택적으로 `.gitignore`를 존중합니다.
* 거대한 디렉터리 트리에서 폭주를 막기 위해 합리적인 한계를 설정합니다(예: 최대 깊이 4~6 레벨, 최대 2000개 디렉터리).

### 이름 충돌 처리

두 스킬이 같은 `name`을 공유하면 결정적인 우선순위 규칙을 적용하세요.

기존 구현체들의 보편적 컨벤션은 다음과 같습니다: **프로젝트 수준 스킬이 사용자 수준 스킬을 오버라이드한다.**

같은 범위 내에서(예: `<project>/.agents/skills/`와 `<project>/.<your-client>/skills/` 양쪽에 같은 `code-review` 스킬이 있을 때) 처음 발견된 것을 쓰든 마지막 발견된 것을 쓰든 무방합니다. 단, 하나를 정하고 일관되게 유지하세요. 충돌이 발생하면 어떤 스킬이 가려졌는지 사용자가 알 수 있도록 경고를 로그로 남기세요.

### 신뢰(trust) 고려 사항

프로젝트 수준 스킬은 작업 중인 저장소에서 옵니다. 이 저장소는 신뢰할 수 없는 출처일 수 있습니다(예: 방금 클론한 오픈소스 프로젝트). 따라서 프로젝트 수준 스킬 로딩을 신뢰성 검사로 게이팅하는 것을 고려하세요. 사용자가 해당 프로젝트 폴더를 신뢰됨으로 표시한 경우에만 로드합니다. 이는 신뢰할 수 없는 저장소가 에이전트의 컨텍스트에 조용히 지침을 주입하는 것을 막아줍니다.

### 클라우드 호스팅 및 샌드박스 에이전트

에이전트가 컨테이너 또는 원격 서버에서 실행된다면 사용자의 로컬 파일시스템에 접근할 수 없습니다. 발견 메커니즘은 스킬 범위에 따라 다르게 동작해야 합니다.

* **프로젝트 수준 스킬**은 가장 쉬운 경우입니다. 에이전트가 클론된 저장소를 다룬다면(샌드박스 내부일지라도), 프로젝트 수준 스킬은 코드와 함께 이동하므로 저장소의 디렉터리 트리에서 스캔할 수 있습니다.
* **사용자 수준 및 조직 수준 스킬**은 샌드박스에 존재하지 않습니다. 외부 출처에서 프로비저닝해야 합니다. 예를 들어 구성 저장소를 클론하거나, 에이전트 설정을 통해 스킬 URL 또는 패키지를 받거나, 웹 UI를 통해 사용자가 스킬 디렉터리를 업로드하게 할 수 있습니다.
* **빌트인 스킬**은 에이전트 배포 아티팩트에 정적 자산으로 패키징하여 외부 페치 없이 모든 세션에서 사용 가능하게 만들 수 있습니다.

스킬이 에이전트에서 사용 가능해지면 그 이후의 라이프사이클(파싱, 공개, 활성화)은 동일하게 동작합니다.

## 2단계: `SKILL.md` 파일 파싱하기

발견된 각 `SKILL.md`에 대해 메타데이터와 본문 콘텐츠를 추출합니다.

### 프런트매터(Frontmatter) 추출

`SKILL.md` 파일은 두 부분으로 구성됩니다. `---` 구분자 사이의 YAML 프런트매터와, 닫는 구분자 뒤에 오는 마크다운 본문입니다. 파싱 방법:

1. 파일 시작 부분의 여는 `---`와 그 뒤의 닫는 `---`를 찾습니다.
2. 그 사이의 YAML 블록을 파싱합니다. `name`과 `description`(필수) 및 선택적 필드를 추출합니다.
3. 닫는 `---` 이후의 모든 내용을 트림한 것이 스킬의 본문 콘텐츠입니다.

프런트매터 필드 전체 집합과 그 제약 조건은 [명세](/specification)를 참조하세요.

### 잘못된 YAML 처리

다른 클라이언트용으로 작성된 스킬 파일은 그 클라이언트의 파서가 어쩌다 받아들였을 뿐인 기술적으로 유효하지 않은 YAML을 포함할 수 있습니다. 가장 흔한 문제는 콜론이 포함된 따옴표 없는 값입니다.

```yaml theme={null}
# 기술적으로 잘못된 YAML — 콜론이 파싱을 망가뜨림
description: Use this skill when: the user asks about PDFs
```

그러한 값을 따옴표로 감싸거나 YAML 블록 스칼라로 변환한 뒤 다시 시도하는 폴백을 고려하세요. 비용을 최소화하면서도 클라이언트 간 호환성을 개선해 줍니다.

### 관대한 검증(Lenient validation)

문제가 있더라도 가능한 한 스킬을 로드하면서 경고를 띄우세요.

* 이름이 부모 디렉터리 이름과 일치하지 않음 → 경고 후 그대로 로드
* 이름이 64자를 초과함 → 경고 후 그대로 로드
* 설명이 누락되었거나 비어 있음 → 스킬을 건너뜀(공개를 위해 설명은 필수임), 오류 로그
* YAML이 완전히 파싱 불가능 → 스킬을 건너뜀, 오류 로그

진단 정보를 기록하여 사용자에게 (디버그 명령, 로그 파일, UI 등에서) 노출할 수 있게 하되, 미관상 문제로 스킬 로딩 자체를 막지는 마세요.

<Note>
  [명세](/specification)는 `name` 필드에 엄격한 제약을 정의합니다(부모 디렉터리와 일치, 문자 집합, 최대 길이). 위의 관대한 접근법은 다른 클라이언트용으로 작성된 스킬과의 호환성을 위해 의도적으로 이러한 제약을 완화한 것입니다.
</Note>

### 무엇을 저장할 것인가

각 스킬 레코드에는 최소한 세 개의 필드가 필요합니다.

| 필드          | 설명                                  |
| ------------- | ------------------------------------ |
| `name`        | 프런트매터에서 가져옴                 |
| `description` | 프런트매터에서 가져옴                 |
| `location`    | `SKILL.md` 파일의 절대 경로           |

이들을 `name`을 키로 하는 인메모리 맵에 저장하여 활성화 시 빠르게 조회할 수 있게 하세요.

발견 시점에 **본문**(프런트매터 다음의 마크다운 콘텐츠)을 같이 저장하거나, 활성화 시점에 `location`에서 읽어올 수도 있습니다. 미리 저장하면 활성화가 더 빠르지만, 활성화 시점에 읽으면 전체 메모리 사용량이 줄고 활성화 사이에 스킬 파일이 변경되어도 반영할 수 있습니다.

스킬의 **베이스 디렉터리**(`location`의 부모 디렉터리)는 나중에 상대 경로를 해석하고 번들된 리소스를 열거하는 데 필요합니다. 필요할 때 `location`에서 도출하세요.

## 3단계: 모델에게 사용 가능한 스킬 공개하기

스킬의 전체 콘텐츠를 로드하지 않은 채로 어떤 스킬이 존재하는지 모델에게 알립니다. 이것이 [점진적 공개의 1계층](#the-core-principle-progressive-disclosure)입니다.

### 스킬 카탈로그 구성

발견된 각 스킬에 대해 `name`, `description`, 그리고 선택적으로 `location`(SKILL.md 파일 경로)을 자신의 스택에 맞는 구조화된 형식(XML, JSON, 불릿 목록 등)으로 포함시키세요.

```xml theme={null}
<available_skills>
  <skill>
    <name>pdf-processing</name>
    <description>Extract PDF text, fill forms, merge files. Use when handling PDFs.</description>
    <location>/home/user/.agents/skills/pdf-processing/SKILL.md</location>
  </skill>
  <skill>
    <name>data-analysis</name>
    <description>Analyze datasets, generate charts, and create summary reports.</description>
    <location>/home/user/project/.agents/skills/data-analysis/SKILL.md</location>
  </skill>
</available_skills>
```

`location` 필드는 두 가지 용도를 가집니다. 파일 읽기 기반 활성화([4단계](#step-4-activate-skills) 참조)를 가능하게 하며, 스킬 본문 내 상대 참조(예: `scripts/evaluate.py`)를 해석할 때 모델에게 기준 경로를 제공합니다. 전용 활성화 도구가 결과에서 스킬 디렉터리 경로를 함께 제공한다면([구조화된 래핑](#structured-wrapping) 참조), 카탈로그에서 `location`을 생략해도 됩니다. 그렇지 않다면 포함시키세요.

각 스킬은 카탈로그에 약 50~100 토큰을 추가합니다. 수십 개의 스킬이 설치되어 있어도 카탈로그는 여전히 작게 유지됩니다.

### 카탈로그를 어디에 둘 것인가

흔히 사용되는 두 가지 방식이 있습니다.

**시스템 프롬프트 섹션**: 카탈로그를 시스템 프롬프트의 라벨링된 섹션으로 추가하고, 앞에 스킬 사용 방법에 대한 간단한 지침을 둡니다. 가장 단순한 방식이며, 파일 읽기 도구에 접근할 수 있는 모든 모델에서 동작합니다.

**도구 설명(Tool description)**: 전용 스킬 활성화 도구의 설명 안에 카탈로그를 임베드합니다([4단계](#step-4-activate-skills) 참조). 시스템 프롬프트를 깔끔하게 유지하고, 발견(discovery)과 활성화(activation)를 자연스럽게 결합시킵니다.

둘 다 유효합니다. 시스템 프롬프트 배치는 더 단순하고 호환성이 넓습니다. 전용 활성화 도구가 있는 경우에는 도구 설명에 임베딩하는 편이 더 깔끔합니다.

### 동작 지침(Behavioral instructions)

카탈로그와 함께 모델에게 스킬을 언제, 어떻게 사용할지 알려주는 짧은 지침 블록을 포함하세요. 문구는 지원하는 활성화 메커니즘에 따라 달라집니다([4단계](#step-4-activate-skills) 참조).

**모델이 파일 읽기로 스킬을 활성화하는 경우:**

```
The following skills provide specialized instructions for specific tasks.
When a task matches a skill's description, use your file-read tool to load
the SKILL.md at the listed location before proceeding.
When a skill references relative paths, resolve them against the skill's
directory (the parent of SKILL.md) and use absolute paths in tool calls.
```

**모델이 전용 도구를 통해 스킬을 활성화하는 경우:**

```
The following skills provide specialized instructions for specific tasks.
When a task matches a skill's description, call the activate_skill tool
with the skill's name to load its full instructions.
```

이러한 지침은 간결하게 유지하세요. 목표는 스킬이 존재한다는 사실과 로드 방법을 알리는 것이며, 상세한 지침은 스킬 콘텐츠 자체가 로드된 뒤에 제공합니다.

### 필터링

일부 스킬은 카탈로그에서 제외되어야 합니다. 흔한 이유는 다음과 같습니다.

* 사용자가 설정에서 해당 스킬을 비활성화함
* 권한 시스템이 해당 스킬에 대한 접근을 거부함
* 스킬이 모델 주도 활성화를 옵트아웃함(예: `disable-model-invocation` 플래그)

**필터링된 스킬은 카탈로그에서 완전히 숨기세요**. 목록에는 보여주고 활성화 시점에 차단하는 방식보다 낫습니다. 모델이 사용할 수 없는 스킬을 로드하려고 시도하면서 턴을 낭비하지 않게 됩니다.

### 사용 가능한 스킬이 없을 때

발견된 스킬이 없다면 카탈로그와 동작 지침을 모두 생략하세요. 비어 있는 `<available_skills/>` 블록을 보여주거나 유효한 옵션이 없는 스킬 도구를 등록하지 마세요. 모델을 혼란스럽게 합니다.

## 4단계: 스킬 활성화

모델 또는 사용자가 스킬을 선택하면, 전체 지침을 대화 컨텍스트에 전달합니다. 이것이 [점진적 공개의 2계층](#the-core-principle-progressive-disclosure)입니다.

### 모델 주도 활성화(Model-driven activation)

대부분의 구현은 하니스 측의 트리거 매칭이나 키워드 감지 대신, 모델 자체의 판단을 활성화 메커니즘으로 사용합니다. 모델은 [3단계](#step-3-disclose-available-skills-to-the-model)의 카탈로그를 읽고, 현재 작업에 어떤 스킬이 관련 있는지 결정한 뒤 로드합니다.

두 가지 구현 패턴이 있습니다.

**파일 읽기 활성화**: 모델은 표준 파일 읽기 도구를 호출하여 카탈로그의 `SKILL.md` 경로를 읽습니다. 특별한 인프라가 필요 없으며, 에이전트의 기존 파일 읽기 기능만으로 충분합니다. 모델은 도구 결과로 파일 콘텐츠를 받습니다. 모델이 파일 접근 권한을 가진 경우 가장 간단한 접근 방식입니다.

**전용 도구 활성화**: 스킬 이름을 받아 콘텐츠를 반환하는 도구(예: `activate_skill`)를 등록합니다. 모델이 파일을 직접 읽을 수 없는 경우에는 필수이며, 가능한 경우에도 선택적으로(그러나 유용하게) 사용할 수 있습니다. 원시 파일 읽기에 비해 다음 장점이 있습니다.

* 반환되는 콘텐츠를 통제할 수 있음(예: YAML 프런트매터 제거 또는 유지, 아래 [모델이 받는 것](#what-the-model-receives) 참조)
* 콘텍스트 관리 시 식별을 위해 구조화된 태그로 콘텐츠를 감쌀 수 있음
* 지침과 함께 번들된 리소스(예: `references/*`) 목록을 함께 제공할 수 있음
* 권한을 강제하거나 사용자 동의를 요청할 수 있음
* 분석을 위해 활성화 이벤트를 추적할 수 있음

<Tip>
  전용 활성화 도구를 사용한다면 `name` 파라미터를 유효한 스킬 이름 집합으로 제한하세요(예: 도구 스키마의 enum). 이는 모델이 존재하지 않는 스킬 이름을 환각하는 것을 방지합니다. 사용 가능한 스킬이 없으면 도구 자체를 등록하지 마세요.
</Tip>

### 사용자 명시적 활성화(User-explicit activation)

사용자도 모델의 결정을 기다리지 않고 직접 스킬을 활성화할 수 있어야 합니다. 가장 흔한 패턴은 하니스가 가로채는 **슬래시 명령 또는 멘션 문법**(`/skill-name` 또는 `$skill-name`)입니다. 구체적인 문법은 자유롭게 정할 수 있습니다. 핵심은 하니스가 조회와 주입을 처리하므로, 모델이 스스로 활성화 동작을 하지 않아도 스킬 콘텐츠를 받게 된다는 점입니다.

사용자가 입력할 때 사용 가능한 스킬 목록을 보여주는 자동 완성 위젯도 발견성을 높이는 데 도움이 됩니다.

### 모델이 받는 것

스킬이 활성화되면 모델은 스킬의 지침을 받습니다. 그 콘텐츠가 정확히 어떤 모습인지에 대해 두 가지 옵션이 있습니다.

**전체 파일**: 모델은 YAML 프런트매터를 포함한 `SKILL.md` 전체를 봅니다. 이는 모델이 원시 파일을 그대로 읽는 파일 읽기 활성화에서 자연스러운 결과입니다. 전용 도구에서도 유효한 선택입니다. 프런트매터는 활성화 시점에 유용한 필드를 포함할 수 있습니다. 예를 들어 [`compatibility`](/specification#compatibility-field)는 환경 요구 사항을 명시하며, 이는 모델이 스킬의 지침을 어떻게 실행할지에 영향을 줄 수 있습니다.

**본문만(프런트매터 제거)**: 하니스가 YAML 프런트매터를 파싱하여 제거하고 마크다운 지침만 반환합니다. 전용 활성화 도구를 가진 기존 구현체 다수가 이 접근을 택합니다. 발견 단계에서 `name`과 `description`을 추출한 뒤 프런트매터를 제거합니다.

실무에서는 두 방식 모두 잘 동작합니다.

### 구조화된 래핑(Structured wrapping)

전용 활성화 도구를 사용한다면 스킬 콘텐츠를 식별 가능한 태그로 감싸는 것을 고려하세요. 예시:

```xml theme={null}
<skill_content name="pdf-processing">
# PDF Processing

## When to use this skill
Use this skill when the user needs to work with PDF files...

[rest of SKILL.md body]

Skill directory: /home/user/.agents/skills/pdf-processing
Relative paths in this skill are relative to the skill directory.

<skill_resources>
  <file>scripts/extract.py</file>
  <file>scripts/merge.py</file>
  <file>references/pdf-spec-summary.md</file>
</skill_resources>
</skill_content>
```

실용적 이점은 다음과 같습니다.

* 모델이 스킬 지침을 다른 대화 콘텐츠와 명확히 구분할 수 있음
* 하니스가 컨텍스트 압축 시 스킬 콘텐츠를 식별할 수 있음([5단계](#step-5-manage-skill-context-over-time))
* 번들된 리소스를 즉시 로드하지 않고도 모델에게 노출할 수 있음

### 번들된 리소스 목록 제공

전용 활성화 도구가 스킬 콘텐츠를 반환할 때, 스킬 디렉터리의 보조 파일(스크립트, 참조 자료, 자산)을 함께 열거할 수 있습니다. 단, **그것들을 적극적으로(읽어서) 미리 로드해서는 안 됩니다.** 모델은 스킬의 지침이 해당 파일을 참조할 때 자신의 파일 읽기 도구를 사용하여 필요한 파일을 그때그때 로드합니다.

스킬 디렉터리가 크다면 목록에 상한을 두고, 목록이 불완전할 수 있음을 명시하세요.

### 권한 허용 목록(Permission allowlisting)

에이전트가 파일 접근을 게이팅하는 권한 시스템을 갖고 있다면, **스킬 디렉터리를 허용 목록(allowlist)에 추가**하여 모델이 사용자 확인 프롬프트 없이 번들 리소스를 읽을 수 있게 하세요. 그렇지 않으면 번들 스크립트나 참조 파일을 참조할 때마다 권한 대화 상자가 발생하여, `SKILL.md` 이외의 리소스를 포함하는 스킬의 흐름이 끊깁니다.

## 5단계: 시간이 지나도 스킬 컨텍스트 관리하기

스킬 지침이 대화 컨텍스트에 들어가면, 세션 기간 내내 효과적으로 유지되도록 관리하세요.

### 컨텍스트 압축으로부터 스킬 콘텐츠 보호

컨텍스트 윈도우가 가득 차서 에이전트가 오래된 메시지를 잘라내거나 요약한다면, **스킬 콘텐츠는 잘라내기(pruning)에서 면제**하세요. 스킬 지침은 지속적인 동작 지침입니다. 대화 도중 잃어버리면 가시적 오류 없이 에이전트의 성능이 조용히 저하됩니다. 모델은 계속 작동하지만, 스킬이 제공하던 전문 지침은 사라진 상태입니다.

흔한 접근 방식:

* 스킬 도구 출력에 보호 플래그를 달아 잘라내기 알고리즘이 건너뛰게 함
* 4단계의 [구조화된 태그](#structured-wrapping)를 이용해 스킬 콘텐츠를 식별하고 압축 중에도 보존함

### 활성화 중복 제거

현재 세션에서 어떤 스킬이 활성화되었는지 추적하는 것을 고려하세요. 모델(또는 사용자)이 이미 컨텍스트에 있는 스킬을 다시 로드하려고 하면, 동일한 지침이 대화에 여러 번 나타나는 것을 막기 위해 재주입을 생략할 수 있습니다.

### 서브에이전트 위임 (선택)

이는 일부 클라이언트에서만 지원되는 고급 패턴입니다. 스킬 지침을 메인 대화에 주입하는 대신, 스킬을 **별도의 서브에이전트 세션**에서 실행합니다. 서브에이전트는 스킬 지침을 받아 작업을 수행하고, 작업 요약을 메인 대화로 반환합니다.

이 패턴은 스킬의 작업 흐름이 복잡하여 전용의 집중된 세션에서 실행하는 편이 유리할 때 유용합니다.
